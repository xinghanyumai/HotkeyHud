# 结论先行

1. 四条需求归并为**一个前置闸门 + 一个状态机**：闸门决定「能不能显示」，状态机决定「什么时候显示、什么时候收」。两者分离，各自可单测。
2. 全部判定必须**无副作用、时钟由外部注入**。否则「短暂按下不弹」这类时序规则无法可靠验证。
3. **熟记名单必须同时作用于「列表」和「闪烁」**。只过滤列表会留下一个坑：按 Ctrl+C 时面板仍会多停留 500ms。这是本规格最容易被实现错的一条。
4. 游戏识别**不追求 100%**。漏判的代价是多显示一次面板（可恢复），误判的代价是用户在游戏里被遮挡（不可接受），因此规则取「宁可多抑制」。
5. 「未打开该软件就不显示」不需要额外逻辑——查询入口本身就是前台进程，天然隔离。真正要防的是**回退到全局快捷键混合展示**。

# 1. 判定总览

按键到达后，按以下顺序过闸。**任一闸门拦截即终止，不再往下判定。**

| 序 | 闸门 | 条件 | 结果 |
|---|---|---|---|
| G1 | 用户暂停 | 托盘已勾选「暂停显示」 | 不显示 |
| G2 | 游戏 / 全屏 | 见 §2 决策表命中 | 不显示 |
| G3 | 应用未收录 | 前台进程无档案，且 `showEmptyState=false` | 不显示（静默） |
| G4 | 已牢记 | 该组合在熟记名单内 | 不显示 / 立即收起 |
| G5 | 时长不足 | 按住未达 `DwellMs` | 不显示 |
| — | 全部通过 | — | 显示面板 |

> G1–G4 是**内容闸门**，可以在按下瞬间判定；G5 是**时序闸门**，只能由状态机在计时到点时判定。

# 2. R1 — 游戏运行时不显示

## 2.1 采集的信号

| 编号 | 信号 | 采集方式 | 说明 |
|---|---|---|---|
| S1 | `ExclusiveFullscreen` | `SHQueryUserNotificationState` ∈ {2 忙, 3 D3D 全屏, 4 演示模式} | 系统级，最可靠 |
| S2 | `CoversWholeMonitor` | `GetWindowRect` 与 `GetMonitorInfo().rcMonitor` 四边差 ≤ 2px | 判断是否铺满整块屏 |
| S3 | `HasCaption` | `(GWL_STYLE & WS_CAPTION) == WS_CAPTION` | 有标题栏 → 不是全屏游戏 |
| S4 | `WindowClass` | `GetClassName` | 引擎特征 |
| S5 | `ExecutablePath` | `QueryFullProcessImageName` | 安装位置特征 |
| S6 | `ProcessName` | 同上取文件名 | 用户名单匹配 |

**采集时机**：前台窗口变化时采集一次，另每 2 秒轮询一次 S1（全屏状态可能不伴随前台切换）。**不要在每次按键时采集**——`OpenProcess` 有实打实的开销。

## 2.2 决策表（按序判定，命中即返回）

| 序 | 条件 | 结论 | 理由 |
|---|---|---|---|
| D1 | S1 为真 | 抑制 | 系统自己都认为处于全屏/演示状态 |
| D2 | S4 ∈ {`UnityWndClass`, `UnrealWindow`, `CryENGINE`, `Valve001`} | 抑制 | 引擎窗口类名稳定，误判率极低 |
| D3 | S6 ∈ 用户维护的游戏名单 | 抑制 | 兜底，用户可自行补 |
| D4 | S5 含 `\steamapps\common\`、`\epic games\`、`\gog games\`、`\ubisoft game launcher\games\`、`\wegameapps\`、`\riot games\`、`\battle.net\` | 抑制 | 覆盖绝大多数发行平台 |
| D5 | S2 为真 且 S3 为假 | 抑制 | 无边框全屏**兜底**：多数机器上 D1 的 `QUNS=2` 会先命中，D5 不会独立触发；保留它是为了覆盖 QUNS 不上报全屏的显示器/系统组合 |
| — | 全部未命中 | 放行 | — |

## 2.3 已知取舍（写进文档，别指望实现时想清楚）

- **窗口化运行的游戏不会被 D1/D5 捕获**，只能靠 D3/D4。装在非标准目录的窗口化游戏会漏判 → 用户手动加名单。
- **D5 会误伤**：PowerPoint 放映、全屏视频、无边框的浏览器 F11。这是有意的——在这些场景弹面板同样不合适。
  **v1.3 决策：删除 `TreatBorderlessFullscreenAsGame` 开关，D5 恒开。**
  理由：S4 真机实测 `QUNS=2` 会先命中 D1，开关在本机永远验证不出效果——暴露一个"按了没反应"的开关比没有开关更糟。
  D5 在其他系统组合下仍可能独立生效，所以规则保留，只去掉开关。
- **「游戏在后台运行」不等于抑制**。本规格只抑制「前台是游戏/全屏」。
  **已确认：采用此解释，不做后台进程轮询。** 理由：轮询成本高、误判率高，且用户切到 Word 时看不到提示属于功能缺失而非 bug。

# 3. R2 — 只显示当前打开软件的快捷键

## 3.1 数据模型

```json
{
  "app": "winword",
  "displayName": "Word",
  "processNames": ["WINWORD.EXE"],
  "shortcuts": [
    { "keys": "Ctrl+K", "action": "插入超链接", "group": "插入" }
  ]
}
```

| 字段 | 必填 | 约束 |
|---|---|---|
| `app` | 是 | 稳定标识，建议等于文件名 |
| `displayName` | 是 | 面板头部展示的应用名 |
| `processNames` | 是 | 可多个；匹配时忽略大小写、忽略 `.exe` 后缀 |
| `shortcuts[].keys` | 是 | 必须可解析为「修饰键 + 单键」；解析失败的条目**静默丢弃并计数** |
| `shortcuts[].action` | 是 | 效果文案，面板上显示的就是它 |
| `shortcuts[].group` | 否 | 缺省归入「常规」；多组时面板显示分组标题 |

## 3.2 查询规则

| 规则 | 说明 |
|---|---|
| 索引键 | 前台窗口的进程名，归一化 = 去 `.exe` + 忽略大小写 |
| 单一入口 | 只有 `FindByProcess(前台进程名)` 一个入口，**不存在**「查不到就退到全局表」的路径 |
| **包含匹配**（v1.5） | 保留**所有包含**当前触发修饰键的组合。`Ctrl` 面板包含 `Ctrl+Shift+K`、`Ctrl+Alt+Del`、`Ctrl+Space`。<br>键帽文字 = 去掉触发修饰键后的部分（`Ctrl+Shift+K` → `Shift+K`）<br>v1.4 及以前是「完全等于」，导致 `Ctrl+Shift+*` 在按 Ctrl 时永远看不到 |
| **排序**（v1.7） | **组优先**（保持档案里的组顺序），组内按「修饰键数量」升序；「通用」组固定排最后。<br>v1.5 是「全局按修饰键数排序」，会把同一组打散，导致一页里出现 5 个组名（Word 实测） |
| 空结果 | 返回空集合，面板显示空状态或静默，**绝不混入其他应用条目** |

## 3.3 未收录应用的处理（需产品决策）

| 方案 | 表现 | 建议 |
|---|---|---|
| A 静默不弹 | 用户不知道工具是否在运行 | 默认 |
| B 弹一行提示「未收录 XX，可添加」 | 有引导，但重复打扰 | 由 `showEmptyState` 开关控制，默认关 |

**推荐 A + 托盘气泡提示**：首次遇到未收录应用时弹一次气泡，之后静默。

## 3.4 用户自定义与自动读取（v1.8）

### 3.4.1 目录与合并

```
%APPDATA%\HotkeyHud\apps\
  _global.json      全局条目，所有应用可见，组名「自定义」
  <exe>.json        应用级条目，与同名内置档案合并
```

| 规则 | 说明 |
|---|---|
| 合并顺序 | 内置先、用户后；**同 `keys` 用户覆盖内置** |
| 降权豁免 | 用户显式写的条目**不受熟记名单降权影响**，正常排在应用组内 |
| 加载失败 | 跳过该文件 + 记入错误列表，不影响其他档案 |
| 进程名 | 由用户在入口处选定 exe 后自动填入，不许手写猜 |

### 3.4.2 自动读取（适配器）

**Windows 没有「读取任意应用快捷键」的通用 API。** 只有「应用自己把键位存在配置文件里」的才能读。

| 适配器 | 识别 | 读取 | 产出 |
|---|---|---|---|
| VS Code | `Code.exe` | `%APPDATA%\Code\User\keybindings.json` | 用户改过的键位（差异化价值最高） |
| JetBrains | `idea64.exe` / `pycharm64.exe` 等 | `%APPDATA%\JetBrains\<product>\keymaps\*.xml` | 用户 keymap |

**只做这两家。** 其余应用（Office、微信、浏览器）没有可读来源，走手动模板。
不要为「看起来支持更多」去猜文件路径——猜错会产出错误键位，比没有更糟。

### 3.4.3 入口

托盘 → 「添加应用快捷键…」：

1. 文件选择器选 exe
2. 尝试匹配适配器：成功 → 生成用户档案并提示「已读取 N 条」
3. 失败 → 生成模板 JSON（含 3 条示例）并打开
4. 完成后自动重载数据

# 4. R3 — 通用且熟知的快捷键始终「已牢记」

## 4.1 语义

「已牢记」= 用户已形成肌肉记忆，**不需要看到它**。因此这类组合有双重效果：不出现在列表里，按下时也不触发高亮。

## 4.2 默认名单

| 类别 | 组合 |
|---|---|
| 剪贴板 | `Ctrl+C` `Ctrl+V` `Ctrl+X` |
| 撤销重做 | `Ctrl+Z` `Ctrl+Y` `Ctrl+Shift+Z` |
| 全选保存 | `Ctrl+A` `Ctrl+S` `Ctrl+Shift+S` |
| 查找打印 | `Ctrl+F` `Ctrl+P` |
| 新建打开关闭 | `Ctrl+N` `Ctrl+O` `Ctrl+W` `Ctrl+T` `Ctrl+Shift+N` `Ctrl+Shift+T` |
| 格式 | `Ctrl+B` `Ctrl+I` `Ctrl+U` |
| 窗口 | `Ctrl+Tab` `Ctrl+F4` |
| ~~系统~~ | **v1.4 起移除**：`Alt+Tab` `Alt+F4` `Win+D` `Win+E` `Win+L` `Win+R` `Win+Tab` 不再过滤 |

> **v1.4 决策**：熟记名单只保留 **Ctrl 单修饰键的高频编辑类**。
> 理由：Alt / Win 面板条目本来就少，过滤它们等于让面板空着；用户实测明确想看到 `Alt+F4`。
> Ctrl 类的肌肉记忆过滤保留——那才是"占满面板"的真凶。

## 4.3 作用点：从「过滤」改为「降权」（v1.7）

> **用户明确要求**：Ctrl+C / Ctrl+V / Ctrl+Z 这类通用键也要能看到。
> 原设计把它们整条剔除，导致「面板里永远没有复制粘贴」——用户认为是缺功能。
> v1.7 起改为：**不剔除，只降权**。

| 作用点 | 旧（v1.6） | 新（v1.7） |
|---|---|---|
| 列表 | 剔除，只计数 | **保留**，归入「通用」组，排在所有应用组之后（最后一页） |
| 闪烁 | 不进入 Flashing，直接收起 | **正常高亮 500ms**，与其他组合一致 |
| 计数 | `HiddenByKnownCount` | `DeferredKnownCount`（被降权而非隐藏的条数） |

**为什么降权而不是取消过滤**：直接放进首页会让 Word 的 38 条里前 6 条全是 Ctrl+C/V/X/Z/A/S，
把应用特有的快捷键挤到第二页——那是另一个方向的「缺功能」。放最后一页两头都满足。

**配置语义不变**：`knownShortcuts: null` = 用内置名单；`[]` = 名单为空，等同于全部按普通条目排序。

第二条最容易漏。判定必须发生在「非修饰键按下」的那一刻，而不是等闪烁计时结束。

## 4.4 配置

- `knownShortcuts: null` → 使用默认名单
- `knownShortcuts: []` → 关闭过滤（面板会包含 Ctrl+C 等）
- `knownShortcuts: [...]` → 完全替换默认名单（不是追加）

---

## 4.5 明确不支持的键（v1.6）

| 键 | 为什么做不到 |
|---|---|
| **`Fn`** | **由键盘固件 / 嵌入式控制器在硬件层处理**，Windows 根本收不到它。没有对应的虚拟键码，`WH_KEYBOARD_LL` 与 Raw Input 都看不到。微软自家的 PowerToys Keyboard Manager 同样不支持重映射 Fn |
| `Copilot` 键 | 部分机型映射为 `Win+Shift+F23`，行为随厂商固件不同，不做保证 |

**不做任何"Fn 面板"**。理由：面板的触发条件是「检测到修饰键按下」，而 Fn 永远不会产生这个信号——做了也永远不显示，属于假功能。

**可替代的**：Fn 组合的**实际效果**（音量、播放）会以标准媒体键到达（`VK_VOLUME_UP` 0xAF、`VK_MEDIA_PLAY_PAUSE` 0xB3 等），但这些是**单键**，不符合"长按修饰键"的触发模型。若将来要做媒体键说明，需单独设计入口，不属于本规格。

# 5. R4 — 短暂按下不弹出

## 5.1 状态定义

| 状态 | 含义 |
|---|---|
| `Idle` | 无待展示意图 |
| `Armed` | 已按下单个修饰键，正在等长按阈值 |
| `Visible` | 面板已展示 |
| `Flashing` | 面板已展示，且刚按下一个具体组合，正在高亮 |

## 5.2 转移表

| 当前 | 事件 | 条件 | 新状态 | 副作用 |
|---|---|---|---|---|
| Idle | 修饰键按下 | 无其他修饰键按住、未阻塞、未被抑制 | Armed | 记录触发键与起始时刻 |
| Idle | 修饰键按下 | 已有其他修饰键 / 阻塞中 / 抑制中 | Idle | 忽略 |
| Armed | 另一个修饰键按下 | — | Idle | 取消（Ctrl+Shift 属组合操作） |
| Armed | **非修饰键按下** | — | Idle | 取消 + 阻塞至全部松开 |
| Armed | 触发键松开 | — | Idle | 取消 |
| Armed | 计时 ≥ `DwellMs` | — | Visible | 请求显示 |
| Visible | 非修饰键按下 | 组合**不在**熟记名单 | Flashing | 高亮该组合，重置闪烁计时 |
| Visible | 非修饰键按下 | 组合**在**熟记名单 | Idle | 立即收起 + 阻塞 |
| Visible | 触发键松开 | — | Idle | 收起 |
| Visible | 另一个修饰键按下 | — | Idle | 收起 + 阻塞 |
| Flashing | 计时 ≥ `FlashMs` | — | Idle | 收起 + 阻塞 |
| Flashing | 非修饰键按下 | 不在熟记名单 | Flashing | 换高亮，重置计时 |
| 任意 | 鼠标键按下 | — | Idle | 取消或收起 |
| 任意 | **滚轮** | — | 不变 | **v1.4 起不再取消**：滚轮作为组合键参与（`Ctrl+滚轮↑` 是缩放），走非修饰键通路 |
| 任意 | 前台窗口切换 | — | Idle | 取消或收起 |
| 任意 | 抑制置真 | — | Idle | 强制收起 |

## 5.3 三个必须写死的细节

1. **取消 ≠ 只是不显示**。取消后要置 `blockedUntilRelease = true`，直到所有修饰键松开前不再进入 Armed。
   否则：Ctrl+C 之后用户还按着 Ctrl，300ms 后会突然弹面板——比不弹更烦。
2. **`DwellMs` 默认 450，范围 80–5000**。
   v1.5 从 300 上调：用户实测「按快捷键老闪菜单」——300ms 与部分人的按键节奏重叠，面板闪一下就消失，比不弹更烦。
   450ms 仍低于 PowerToys 的 900ms 默认值，查询意图不会落空。低于 200ms 正常打字必闪，高于 800ms 查询会明显变慢。
3. **只认第一个按下的修饰键**。先按 Shift 再按 Ctrl，不触发。这是刻意的，用来排除 Ctrl+Shift 类组合。

## 5.4 典型时序（Ctrl+C）

| 时刻 | 事件 | 状态 | 面板 |
|---|---|---|---|
| 0ms | Ctrl 按下 | Armed | 无 |
| 60ms | C 按下 | Idle（取消 + 阻塞） | 无 |
| 90ms | C 松开 | Idle | 无 |
| 130ms | Ctrl 松开 | Idle（解除阻塞） | 无 |

## 5.5 典型时序（长按查询）

| 时刻 | 事件 | 状态 | 面板 |
|---|---|---|---|
| 0ms | Ctrl 按下 | Armed | 无 |
| 300ms | 计时到点 | Visible | 显示 |
| 800ms | K 按下 | Flashing | 高亮 Ctrl+K |
| 1300ms | 闪烁结束 | Idle | 收起 |

---

## 5.6 分页（v1.5）

条目超过一页时分页，**不再截断丢弃**。

| 项 | 规则 |
|---|---|
| 每页条数 | 12（与 §6.1 上限一致） |
| 页数 | `ceil(总条数 / 12)`，至少 1 |
| 上一页 | `↑` |
| 下一页 | `↓` |
| 翻页后 | **面板尺寸不变**（固定 12 格高），避免重建 DIB 造成闪烁 |
| 页码指示 | 多页：`第 1/4 页 · ↑↓ 翻页 · 松开 Ctrl 隐藏`<br>单页：`共 8 条 · 松开 Ctrl 隐藏` |
| 翻页键代价 | `Ctrl+↑/↓`（Word 段落跳转）、`Alt+↑`（资源管理器上一级）、`Win+↑/↓`（最大化/还原）在面板可见期间失效。**这是用户明确接受的代价**；靠「单页不装钩子」+「450ms 阈值」把影响压到最小 |
| 末页不满 | 留白，不缩高 |

**翻页键必须被吞掉**，不能传给前台应用——否则 `Ctrl+↓` 会同时翻页和滚动文档。

实现：**仅当总条数 > 12（即真有多页）时**，面板可见期间安装 `WH_KEYBOARD_LL`，命中 `↑`/`↓` 返回 1；面板收起立即卸钩。
**单页时完全不装钩子**——绝大多数情况下用户根本不会感觉到输入被拦截。钩子只在可见期间存在，不常驻。

**安全阀**：面板显示超过 **15 秒**强制收起并卸钩。
防止 key-up 丢失导致钩子长期挂着、把用户的翻页键全部吃掉。

**已知限制**：提权窗口前台时 LL 钩子无效（UIPI），翻页键会漏给应用。

# 6. 数据契约（UI 层只消费，不判定）

| 字段 | 类型 | 说明 |
|---|---|---|
| `appName` | string | 面板标题 |
| `modifier` | enum | 触发键，决定强调色 |
| `groups[]` | array | 已按展示顺序排好，UI 不再排序 |
| `groups[].items[]` | array | 每项含「键」「效果文案」 |
| `totalCount` | int | 过滤后的可见条目总数 |
| `hiddenByKnownCount` | int | 被熟记名单剔除的数量，用于底部提示 |
| `hasProfile` | bool | 是否有该应用档案，决定空状态文案 |

**边界约定**：UI 层不得过滤或补全条目，**不得改变组内顺序**。
为列平衡允许跨组重排，但必须满足三条不变量：每组都带组名、跨列必标「（续）」、**同一组最多跨 2 列**。

# 8. 风险与未验证项

| 等级 | 项 | 说明 | 应对 |
|---|---|---|---|
| `[RISK]` 高 | 提权窗口前台时收不到输入 | UIPI 会阻断 Raw Input 与低层钩子 | 接受限制并文档说明；不要为此要求管理员权限，那会显著提高杀软告警等级 |
| `[RISK]` 高 | 杀软把「全局输入监听 + 置顶透明窗」判为键盘记录器 | 特征组合高度相似 | 代码签名、零日志、零联网、开源 |
| `[RISK]` 中 | 窗口化游戏漏判 | 只靠路径与类名，装非标准目录会漏 | 用户名单兜底 |
| `[RISK]` 中 | 无边框全屏误判 | 演示/放映/全屏视频也被抑制 | 提供开关 |
| `[UNVERIFIED]` | 300ms 阈值是否为最优 | 未做真人测试 | 上线前用 5 名用户各试 3 天，记录误触发率 |
| `[UNVERIFIED]` | 熟记名单是否过长 | 剔除过多会让面板显得空 | 统计实际剔除比例，若 > 60% 则收窄名单 |
