# v1.0 发布检查单

## 一、阻塞项（3 项）

### 1. 代码签名 ❌

```
Get-AuthenticodeSignature dist\HotkeyHud\HotkeyHud.App.exe
→ NotSigned
```

**为什么阻塞**：本工具的特征组合是「全局输入监听 + 开机自启 + 置顶透明窗」，这是杀软启发式引擎的典型键记录器画像。无签名时：

- SmartScreen 首次运行弹「Windows 已保护你的电脑」，多数用户会点"不运行"
- Defender / 360 / 火绒 的误报率显著高于已签名程序

**要什么**：OV 证书（约 ¥1000–2000/年）或 EV 证书（约 ¥3000+/年，需硬件 token）。
个人开发者可选 OV；EV 免 SmartScreen 积累期，但成本高。

**做不了签名的替代方案**：在 README 显著位置说明「无签名，首次运行请点『更多信息 → 仍要运行』」，并附 SHA256 校验值供用户核对。

### 2. 干净机器验证 ❌

自包含发布**原理上**不需要 .NET，但未实测。

**怎么验**：找一台没装 .NET 10 Desktop Runtime 的 Windows 10/11，双击 `HotkeyHud.App.exe`：

| 检查 | 期望 |
|---|---|
| 能启动 | 托盘出现 |
| 面板能弹 | 记事本长按 Ctrl |
| 设置页能开 | 托盘 → 设置 |
| 无缺失 DLL 报错 | 事件查看器无 .NET 相关错误 |

没有第二台机器时，可用 Windows 沙盒（`Windows Sandbox`）——但沙盒自带 .NET 4.x 而非 .NET 10，仍可验证自包含是否生效。

### 3. 杀软扫描 ⚠️ 部分完成

至少两家：

| 工具 | 怎么扫 |

## 二、体积优化 ✅ 已完成（结论：压缩本来就已经开着）

**先纠正一个前提**：当前 `dist` 的 49.4 MiB **已经是压缩后的体积**。S8 打包时用的命令里
一直带着 `-p:EnableCompressionInSingleFile=true`，只是没写进 csproj，所以从命令行看不出来。

2026-11-20 实测（同一份代码，只差压缩开关）：

| 配置 | 体积 |
|---|---|
| 自包含 + 单文件，**不压缩** | 116,246,628 字节 = **110.9 MiB** |
| 自包含 + 单文件，**压缩** | 51,765,386 字节 = **49.4 MiB** |

所以「49.4 → 25–30 MB」这一档在 .NET 单文件压缩下**不存在**：压缩已经吃掉了 61 MiB。
再往下只能靠裁剪（被 NETSDK1175 拒绝）或换技术栈。

**冷启动实测**（清空 `%TEMP%\.net\HotkeyHud.App` 解压缓存后，测「进程启动 → 单实例互斥就绪」）：

| 版本 | 冷启动 | 预热 |
|---|---|---|
| 压缩 | **378 ms** | 399 ms |
| 不压缩 | 305 ms | 231 ms |

压缩的代价约 50–150 ms，远低于 1.5 s 门槛 → **保留压缩**。

原始记录：

现状 **49.4 MB**（自包含 + 单文件，未裁剪）。

裁剪不可用是对的——`NETSDK1175`：WinForms 官方不支持裁剪。我此前在提示词里写的「25–35 MB」是按通用项目估的，对 WinForms 不成立，**这条是我的估算错误**。

**但还有一招没试**：单文件压缩。

```xml
<PublishSingleFile>true</PublishSingleFile>
<SelfContained>true</SelfContained>
<EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
```

预期 49.4 → **25–30 MB**。代价：首次启动多 100–300ms（解压到临时目录）。

| 结论 | 条件 |
|---|---|
| 采用 | 冷启动 ≤ 1.5s 可接受 |
| 不采用 | 用户对启动速度敏感，或压缩后杀软误报率上升 |

**先测冷启动再决定**，不要凭感觉。

按顺序做完，任何一步失败都回退：

| # | 步骤 | 通过标准 |

| 1 | 干净机器双击 | 托盘出现，无报错 |

第 6 步要**真重启**，不要只看注册表写了没写——启动时机问题只有重启才暴露。

## 三点五、两个容易漏的安装细节

| # | 项 | 现状 | 处理 |
|---|---|---|---|
| 1 | **开发期自启残留** | 注册表 `HKCU\...\Run\HotkeyHud` 仍指向 `src\HotkeyHud.App\bin\Debug\net10.0-windows\HotkeyHud.App.exe` | 发布前删掉该值，或让用户在发布版托盘里「自启」关一次再开一次，让路径指向新位置 |
| 2 | **`Data` 目录必须与 exe 同目录** | 发布包已含 `dist\HotkeyHud\Data\apps\*.json` | README 必须写「整个文件夹一起复制」。**只拷 exe 会变成 0 个应用档案**，现象是「所有应用都显示未收录」 |

第 1 条是实测发现的：自启项从开发期一直挂着，每次登录启动的是 Debug 版。
如果发布前不清理，用户装完会同时存在「Debug 版自启」和「发布版手动启动」两个来源（单实例会挡住第二个，但报错信息会让人困惑）。

第 2 条是最容易踩的坑：单文件发布给人「一个 exe 就是全部」的错觉，但档案是外置的。

## 四、必须写进发布说明的已知限制

这些不是 bug，是边界。**不写清楚，用户会当成 bug 来报。**

| 限制 | 说明 |
|---|---|
| 不支持 Fn | 键盘固件层处理，Windows 收不到 |
| 提权窗口无响应 | UIPI 阻断，任务管理器等以管理员运行的程序里不弹 |
| 独占全屏不显示 | 游戏内不弹 |
| 只收录 7 个应用 | Word / Chrome / Edge / VS Code / 资源管理器 / 记事本 / 系统 |
| 微信 / QQ / 网易云 / 豆包无档案 | 无官方快捷键文档，需用户自建 |
| 翻页键被吞 | 面板可见期间 `↑` `↓` 不传给前台应用 |
| 混合 DPI 未实测 | 单屏验证通过，双屏不同缩放未验证 |
| 设置页改动不跟随内置升级 | 一旦编辑过某应用，该应用不再接收内置档案更新 |
